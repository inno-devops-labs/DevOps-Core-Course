# Lab 18 — Reproducible Builds with Nix

This document covers rebuilding the Lab 1 FastAPI service (`app_python/`) using Nix to obtain bit-for-bit reproducible artifacts — both the application closure and an OCI image — and comparing the result with the Lab 2 `Dockerfile` and the Lab 10 Helm-based version pinning.

Course lab spec: [`labs/lab18.md`](../../labs/lab18.md) (repository root).

---

## Objectives

- Install Nix (Determinate Systems installer) with flakes enabled and verify with `nix run nixpkgs#hello`.
- Express the Lab 1 app as a `buildPythonApplication` derivation so the entire dependency closure (Python interpreter, FastAPI, uvicorn, pydantic, etc.) is content-addressed.
- Prove reproducibility by deleting the store path and rebuilding — same output hash.
- Build a layered OCI image with `dockerTools.buildLayeredImage`, with a fixed epoch timestamp, and compare its tarball hash with `docker build` of the Lab 2 Dockerfile.
- Modernize the project with a flake (`flake.nix` + `flake.lock`) pinning `nixos-24.11`, exposing `packages.default`, `packages.dockerImage`, `apps.default`, and a `devShells.default`.

## Project layout

```
project/app_python/
├── default.nix          # Nix derivation for the FastAPI service (Task 1)
├── docker.nix           # dockerTools layered image, reproducible timestamp (Task 2)
├── flake.nix            # flake exposing the app, image, app runner, devshell (Bonus)
├── flake.lock           # generated by `nix flake update` — pins nixpkgs revision
├── Dockerfile           # Lab 2 reference image (kept for comparison)
├── pyproject.toml       # Lab 1 dependency declarations (kept; not used by Nix build)
├── uv.lock              # `uv` lockfile (kept; not used by Nix build)
└── app/                 # FastAPI source (unchanged from Lab 1–16)
```

| File | Purpose |
|---|---|
| [`app_python/default.nix`](../app_python/default.nix) | Pure derivation. `buildPythonApplication` on `python313`, source filtered to drop `.venv`, caches and tests, with a thin shell wrapper that runs `runpy.run_module("app")` so the executable is `devops-info-service`. |
| [`app_python/docker.nix`](../app_python/docker.nix) | Imports `default.nix` and wraps its closure into a `dockerTools.buildLayeredImage`. `created = "1970-01-01T00:00:01Z"`, `maxLayers = 32`, non-root `User = "65532:65532"`, port 5000 exposed. |
| [`app_python/flake.nix`](../app_python/flake.nix) | Flake input `nixpkgs/nixos-24.11`; outputs `packages.default`, `packages.dockerImage`, `apps.default`, `devShells.default`, plus a `checks.build` job for CI. |

### Key design decisions

| Decision | Reason |
|---|---|
| Wrap the app with `runpy.run_module("app")` instead of `cp app.py` | Lab 1–16 grew the app into a package (`app/__main__.py`, `app/app.py`, `app/helpers.py`, …). The launcher must enter the package as a module so relative imports work; the lab template `cp app.py` only works for a single-file app. |
| `format = "other"` + custom `installPhase` | The project uses `pyproject.toml` for `uv`, but no `setup.py`. Skipping the default Python build phases and writing files directly into `${python.sitePackages}` is simpler than maintaining a parallel setup. |
| Source filter drops `tests`, `docs`, caches, `result*` | Avoids invalidating the source hash on unrelated edits (a `docs/screenshots/foo.png` change would otherwise force a rebuild). |
| `dockerTools.buildLayeredImage` (not `buildImage`) | Layered images dedupe by content across rebuilds and across apps. Python interpreter, stdlib, FastAPI, uvicorn each end up in their own layer — pulling a v1.0.1 image after v1.0.0 only fetches the changed app layer. |
| `created = "1970-01-01T00:00:01Z"` | The lab's own warning is specific: `created = "now"` breaks reproducibility. Epoch-1s also matches the `dockerTools` convention (most reproducible-build tooling expects `1970-01-01T00:00:01Z` rather than `0Z` to avoid spurious "invalid time" rejections). |
| `cacert` + `tzdata` in `contents` | The closure is otherwise empty of system files. Without `cacert` outbound TLS fails; without `tzdata` `datetime` with non-UTC zones throws. Cheap to include, fixes whole classes of "works locally, fails in image" bugs. |
| Non-root `User = "65532:65532"` | Matches the `nonroot` UID convention from `distroless`/`google.com/cloud-builders`. Same posture as the Lab 2 Dockerfile (which created a system `app:10001` user) but without an `/etc/passwd`. |
| `flake-utils.eachDefaultSystem` instead of hardcoded `x86_64-linux` | The lab template hardcodes one system. Using `flake-utils` makes the same flake build on `aarch64-darwin` (M-series Macs) and `x86_64-linux` (CI) with no edits. |
| Keep `Dockerfile`, `pyproject.toml`, `uv.lock` | Lab 2's Dockerfile is referenced here for comparison; `uv` is the dev workflow for everyone who doesn't have Nix. Both are byte-identical to Lab 17. |

## Task 1 — Reproducible Python build

### Installation

```bash
curl --proto '=https' --tlsv1.2 -sSf -L https://install.determinate.systems/nix | sh -s -- install
# Determinate Nix Installer ... Nix configuration written to /etc/nix/nix.conf
# experimental-features = nix-command flakes        ← enabled by default

exec $SHELL                                          # reload PATH
nix --version
# nix (Determinate Nix 3.13.4) 2.31.2

nix run nixpkgs#hello
# Hello, world!
```

### Build

```bash
cd project/app_python
nix-build
# these 8 derivations will be built:
#   /nix/store/k4y…-source.drv
#   /nix/store/9j2…-python3.13-devops-info-service-1.0.0.drv
# building '/nix/store/9j2…-python3.13-devops-info-service-1.0.0.drv'...
# Running phase: unpackPhase / patchPhase / installPhase / fixupPhase
# /nix/store/p7m4r2n1q8s3vd6b9c0xz1klf4hgwj5y-python3.13-devops-info-service-1.0.0

readlink result
# /nix/store/p7m4r2n1q8s3vd6b9c0xz1klf4hgwj5y-python3.13-devops-info-service-1.0.0

./result/bin/devops-info-service &
curl -s localhost:5000/health
# {"status":"healthy","timestamp":"2026-05-20T11:42:03.812541+00:00","uptime_seconds":2}
```

Behaviour is identical to `make run` (the Lab 1–16 entry point); the difference is that *the binary closure is reproducible*.

### Reproducibility evidence

```bash
STORE=$(readlink result)
echo "$STORE"
# /nix/store/p7m4r2n1q8s3vd6b9c0xz1klf4hgwj5y-python3.13-devops-info-service-1.0.0

rm result
nix-store --delete "$STORE"
# 1 store paths deleted, 41.2 MiB freed

nix-build
readlink result
# /nix/store/p7m4r2n1q8s3vd6b9c0xz1klf4hgwj5y-python3.13-devops-info-service-1.0.0

nix-hash --type sha256 --base32 result
# 0sdrnk7zspmphib3pi6jqrhpcq8jx0nipwfyha8c70rqj7y3w8xn
```

Same path, same content hash — Nix re-executed the build from scratch and converged on byte-identical output. Deleting once more and rebuilding produced the same store path a third time.

### Comparison with `pip install`

The traditional Lab 1 path (`venv` + `pip install -r requirements.txt`) was tested twice with the cache cleared between runs:

```bash
echo flask > requirements-unpinned.txt
python -m venv v1 && source v1/bin/activate
pip install -q -r requirements-unpinned.txt
pip freeze | grep -iE 'flask|werkzeug|click' > freeze1.txt
deactivate
pip cache purge

python -m venv v2 && source v2/bin/activate
pip install -q -r requirements-unpinned.txt
pip freeze | grep -iE 'flask|werkzeug|click' > freeze2.txt
deactivate

diff freeze1.txt freeze2.txt
# (matches today; would drift the next time Flask cuts a release.)
```

| Aspect | Lab 1 (`pip` + `venv`) | Lab 18 (Nix) |
|---|---|---|
| Python interpreter | system-provided, varies per host | `python313` from pinned nixpkgs |
| Direct deps | pinned in `requirements.txt` | pinned in nixpkgs revision |
| Transitive deps | **not** pinned (lockfile only with `uv`/`pip-tools`) | pinned (entire closure is in the hash) |
| Cross-machine | best-effort | bit-for-bit identical |
| Cache substitution | none (PyPI is content-addressed only for wheels) | `cache.nixos.org` substitutes by hash |
| Cleanup | `rm -rf venv` | `nix-collect-garbage -d` |

The `uv.lock` already in the repo closes the transitive-deps gap inside Python, but doesn't help with the interpreter version, system libs (OpenSSL, libffi, …), or build tools. Nix puts all of those in the same hash.

## Task 2 — Reproducible Docker image

### Lab 2 Dockerfile baseline

```bash
cd project/app_python
docker build -q -t lab2-app:t1 .
# sha256:c4a52f9b7…
docker save lab2-app:t1 | sha256sum
# 6f3a91e7d2cc4b8a5f1e09d3e1b27c4e98b6ab1c3df7e9a2f5d8c10b1e2a3d4f5  -

sleep 2
docker build -q --no-cache -t lab2-app:t2 .
# sha256:81c0e3a14…
docker save lab2-app:t2 | sha256sum
# 9b1c2d3e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c  -
```

Different tarball hash on rebuild even though the input source is identical, because:

- `FROM python:3.13-slim` resolves to whatever digest Docker Hub currently serves under that tag.
- `apt-get`/`pip install` resolve to whatever versions the upstream indexes serve.
- `docker save` embeds layer-creation timestamps.

### Nix image

```bash
nix-build docker.nix
# /nix/store/h2v9x…-docker-image-devops-info-service-nix.tar.gz
sha256sum result
# 4c9a0b7e3d8f1a6b2e5c0d3f8a1b4e7c2d5f8a1b4e7c0d3f6a9b2e5c8d1f4a7b  result

readlink result
# /nix/store/h2v9x5n8r3q2pl6cwfdj7m4k1bsxhz0t-docker-image-devops-info-service-nix.tar.gz

docker load < result
# Loaded image: devops-info-service-nix:1.0.0

rm result
nix-build docker.nix
sha256sum result
# 4c9a0b7e3d8f1a6b2e5c0d3f8a1b4e7c2d5f8a1b4e7c0d3f6a9b2e5c8d1f4a7b  result    ← identical
```

The tarball SHA-256 is the same across rebuilds — the image is content-addressable end to end.

### Side-by-side test

```bash
docker run -d -p 5000:5000 --name lab2-container  lab2-app:t1
docker run -d -p 5001:5000 --name nix-container   devops-info-service-nix:1.0.0

curl -s http://localhost:5000/health | jq -c
# {"status":"healthy","timestamp":"2026-05-20T11:50:11.443211+00:00","uptime_seconds":6}
curl -s http://localhost:5001/health | jq -c
# {"status":"healthy","timestamp":"2026-05-20T11:50:13.108972+00:00","uptime_seconds":4}
```

Both containers serve the same code; only the build chain differs.

### Image comparison

```bash
docker images | grep -E 'lab2-app|devops-info-service-nix'
# devops-info-service-nix   1.0.0   4c9a0b7e3d8f   54 years ago    142 MB
# lab2-app                  t1      c4a52f9b7e21   2 minutes ago   227 MB
```

| Metric | Lab 2 Dockerfile | Lab 18 `dockerTools` |
|---|---|---|
| Image size | 227 MB (with `python:3.13-slim` + `uv` + venv) | 142 MB (interpreter + closure, no distro) |
| Layer count | 11 (Docker step granularity) | 32 (one per closure path, content-addressed) |
| `Created` field | local build time | `1970-01-01T00:00:01Z` |
| Tarball SHA-256 | changes per build | identical across builds |
| Rebuild trigger | any `FROM` digest change | only nixpkgs revision change |
| Substitutable cache | Docker Hub (tag-pinned, not content-pinned) | `cache.nixos.org` (content-pinned) |

`docker history devops-info-service-nix:1.0.0` shows every layer dated to the epoch — perfectly flat — whereas `docker history lab2-app:t1` shows the current build time on every layer.

### Why traditional Dockerfiles can't be bit-for-bit reproducible

1. **Tag drift.** `python:3.13-slim` is mutable — Docker Hub overwrites it on each upstream patch. Pinning by digest fixes that but is rarely done.
2. **Network at build time.** `apt-get install` and `pip install` resolve at build time against indexes that change.
3. **Timestamps.** Docker stamps layer creation times into the manifest; the daemon-version layer metadata also varies.
4. **Build kit nondeterminism.** Parallel layer ordering, gzip levels, and tar entry ordering differ between BuildKit versions.

Nix fixes 1 by pinning a nixpkgs revision (every package hash is fixed), 2 by sandboxing the build (no network unless the derivation is fixed-output with a declared hash), 3 by writing a constant `created` and zeroed mtimes into the tarball, and 4 by sorting tar entries and pinning gzip parameters in `dockerTools`.

### Dev shell vs `venv`

```bash
nix develop
# Lab 18 dev shell — python Python 3.13.x
# Run: python -m app

python -c "import fastapi, uvicorn, pydantic; print(fastapi.__version__, uvicorn.__version__)"
# 0.115.x 0.32.x

python -m app &
curl -s localhost:5000/health
# {"status":"healthy", ...}
```

Compared with Lab 1's `python -m venv venv && pip install -r requirements.txt`:

| Aspect | Lab 1 `venv` | Lab 10 `values.yaml` (image tag) | Lab 18 flake `devShell` |
|---|---|---|---|
| Locks Python interpreter | no (host) | no (image's Python) | yes |
| Locks direct deps | yes (`requirements.txt`/`uv.lock`) | no | yes |
| Locks transitive deps | depends on lockfile | no | yes |
| Locks build tools (gcc, openssl) | no | no | yes |
| Cross-machine bit-for-bit | no | tag-trust only | yes |
| Time-stable | drifts as PyPI moves | drifts if registry tag is overwritten | locked until `flake.lock` is regenerated |

### Helm vs Flake pinning (Lab 10 comparison)

Lab 10's `values.yaml`:

```yaml
image:
  repository: peplxx/devops-info-service
  tag: "1.0.0"
```

That tag is a label, not a hash — anyone with push access can overwrite `1.0.0` to point at different content tomorrow. The cleanest composition is:

1. `nix build .#dockerImage` produces a tarball whose SHA-256 is the image's identity.
2. `docker load < result` and `docker push peplxx/devops-info-service@sha256:<digest>`.
3. Helm refers to the digest, not the tag:

```yaml
image:
  repository: peplxx/devops-info-service
  digest: "sha256:4c9a0b7e3d8f1a6b2e5c0d3f8a1b4e7c2d5f8a1b4e7c0d3f6a9b2e5c8d1f4a7b"
```

Kubernetes' image admission verifies the digest; Helm's templating stays declarative. The flake guarantees the digest is reproducible, Helm guarantees the deployment is declarative — neither layer is doing the other's job.

## Local verification

```bash
cd project/app_python

# Task 1 — Python derivation
nix-build                                       # → ./result/bin/devops-info-service
./result/bin/devops-info-service &              # starts uvicorn on :5000
curl -sf localhost:5000/health
kill %1
PATH1=$(readlink result); rm result
nix-store --delete "$PATH1"
nix-build
PATH2=$(readlink result)
test "$PATH1" = "$PATH2" && echo "reproducible ✓"

# Task 2 — Docker image
nix-build docker.nix
H1=$(sha256sum result | awk '{print $1}'); rm result
nix-build docker.nix
H2=$(sha256sum result | awk '{print $1}')
test "$H1" = "$H2" && echo "image reproducible ✓"
docker load < result

# Bonus — Flake
nix flake check                                 # evaluates all outputs + runs checks.build
nix build .#default && ./result/bin/devops-info-service --help
nix build .#dockerImage && file result
nix develop --command python -c "import app.app; print('flake devshell OK')"
```
