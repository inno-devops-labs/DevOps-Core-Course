# Lab 16 — Monitoring and Init Containers

This document records the Laboratory 16 exercise on Kubernetes monitoring (kube-prometheus-stack) and init-container patterns. The monitoring stack was installed from Helm chart `prometheus-community/kube-prometheus-stack` (release name `monitoring`, chart version **69.4.1**, application version **v0.79.2**). The course application image is `nexonm22/devops-info-service:lab12`, as declared in `k8s/devops-info-service/values.yaml`. Source repository: `https://github.com/nexonm22/DevOps-Core-Course.git`.

Workload context: namespace `default` contains the Deployment `devops-info-service`. The Lab 15 StatefulSet is named `lab15-app` in namespace `dev`, with pods `lab15-app-0` through `lab15-app-2`.

---

## 1. Stack components

**Prometheus Operator**

The Prometheus Operator is a Kubernetes controller that reconciles custom resources (for example `Prometheus` and `ServiceMonitor`) into a running Prometheus configuration. Creation or modification of those resources triggers reconciliation, which reduces the need for large hand-maintained static configuration files.

**Prometheus**

Prometheus scrapes time-series metrics from HTTP endpoints on a configured interval and stores them locally. The stored series support ad hoc querying, dashboard visualization, and alerting rules.

**Alertmanager**

Alertmanager ingests alerts generated by Prometheus and applies grouping, inhibition, and routing. It supports notification channels (for example e-mail or chat integrations) and maintenance windows via silences.

**Grafana**

Grafana provides visualization and dashboarding on top of Prometheus (and other data sources). The kube-prometheus-stack chart ships curated Kubernetes dashboards. Administrative access in this lab was obtained via `kubectl port-forward` to the Grafana Service.

**kube-state-metrics**

kube-state-metrics exposes the state of Kubernetes API objects (Pods, Deployments, and so on) as metrics—for example readiness counts. It does not substitute for cAdvisor-style process resource metrics.

**node-exporter**

node-exporter runs as a DaemonSet so that each node exposes host-level metrics derived from `/proc` and `/sys` (CPU, memory, disk, and related statistics).

## 4. Init containers

### Repository artifacts

- `k8s/init-containers/init-download.yaml` — downloads content into a shared volume, then serves it with nginx.
- `k8s/init-containers/wait-for-service.yaml` — blocks the main container until Service DNS for `myservice` resolves.

### init-download.yaml (full manifest)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: init-download-pod
spec:
  initContainers:
    - name: init-download
      image: busybox:1.36
      command:
        - sh
        - -c
        - wget -O /work-dir/index.html https://example.com
      volumeMounts:
        - name: workdir
          mountPath: /work-dir
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80
      volumeMounts:
        - name: workdir
          mountPath: /usr/share/nginx/html
  volumes:
    - name: workdir
      emptyDir: {}
```

**Field reference (selected keys)**

- `apiVersion: v1` — Core API group version `v1`.
- `kind: Pod` — Resource type Pod.
- `metadata.name` — Identifier used with subsequent `kubectl` commands.
- `spec.initContainers` — Init containers run to completion before main containers start.
- `initContainers[].image` — `busybox` image used solely for the download step.
- `initContainers[].command` — Invokes `wget` to persist remote content into the shared volume.
- `initContainers[].volumeMounts` — Mounts the shared volume at `/work-dir` in the init container.
- `spec.containers` — Primary workload after successful init completion.
- `containers[].image` — `nginx` serves static content for the demonstration.
- `volumeMounts` (nginx) — Maps the shared volume to `/usr/share/nginx/html` (document root).
- `spec.volumes` — `emptyDir` volume `workdir` shared between init and application containers.

### wait-for-service.yaml (full manifest)

Applying the combined manifest on a clean namespace creates the Pod and Service in a single transaction; both objects appear together:

```
$ kubectl apply -f k8s/init-containers/wait-for-service.yaml
pod/wait-pod created
service/myservice created
```

The committed manifest follows.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: wait-pod
spec:
  initContainers:
    - name: wait-for-service
      image: busybox:1.36
      command:
        - sh
        - -c
        - until nslookup myservice; do echo waiting for myservice; sleep 2; done
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: myservice
spec:
  ports:
    - port: 80
      targetPort: 8080
```

**Field reference (selected keys)**

- `metadata.name: wait-pod` — Pod under test.
- `initContainers[].command` — Polls `nslookup myservice` until cluster DNS succeeds.
- `containers` — Primary nginx container starts only after the init loop terminates successfully.
- Document separator (`---`) — Splits Pod and Service definitions within one file.
- `kind: Service` — Establishes cluster DNS for `myservice`.
- `metadata.name: myservice` — Name resolved by the init container.
- `spec.ports` — Declares Service port **80** (sufficient for DNS existence; `targetPort` is illustrative for the lab).

### Production rationale

Production workloads frequently depend on databases or peer APIs that must be reachable before the primary process starts. Init containers enforce ordering: they may block on DNS resolution or TCP readiness, thereby reducing restart storms caused by premature main-container startup. Logs emitted from the init phase provide a dedicated signal path for diagnosing missing dependencies, which supports safer rollouts and more efficient troubleshooting than unconstrained concurrent startup.
