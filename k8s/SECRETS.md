# Lab 11 - Kubernetes Secrets and HashiCorp Vault

This document captures the implementation and verification for Lab 11 using the Helm chart in `k8s/devops-info`.

## 1. Kubernetes Secrets Fundamentals

### 1.1 Create a Secret with kubectl

```bash
kubectl create secret generic app-credentials \
  --from-literal=username=lab-user \
  --from-literal=password=lab-password
```

Output:

```text
secret/app-credentials created
```

### 1.2 View and decode

```bash
kubectl get secret app-credentials -o yaml
```

Output:

```yaml
apiVersion: v1
data:
  password: bGFiLXBhc3N3b3Jk
  username: bGFiLXVzZXI=
kind: Secret
metadata:
  creationTimestamp: "2026-04-09T10:01:58Z"
  name: app-credentials
  namespace: default
  resourceVersion: "475"
  uid: d34f55be-072b-4ad8-9b8b-f2eb3259c10a
type: Opaque
```

Decode:

```bash
echo "bGFiLXVzZXI=" | base64 -d
echo "bGFiLXBhc3N3b3Jk" | base64 -d
```

Decoded values output:

```text
USERNAME_DECODED=lab-user
PASSWORD_DECODED=lab-password
```

### 1.3 Base64 encoding vs encryption

- Base64 is reversible encoding for transport/storage format; it does not provide confidentiality.
- Encryption requires a key and protects data from unauthorized readers.
- Kubernetes Secret values are base64-encoded in manifests/API responses.

### 1.4 Security implications

- Kubernetes Secrets are not strongly protected by default if etcd encryption at rest is not enabled.
- Production clusters should enable etcd encryption at rest and enforce strict RBAC.
- Limit who can run `get/list/watch` on secrets and audit secret access.

## 3. Resource Management

### 3.1 Current settings

Configured in `k8s/devops-info/values.yaml`:

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "200m"
    memory: "256Mi"
```

### 3.2 Requests vs limits

- Requests reserve CPU/RAM for scheduling and baseline runtime guarantees.
- Limits cap maximum consumption and prevent noisy-neighbor behavior.
- Typical starting point for small stateless services is limit ~= 2x request, then tune from metrics.

## 4. Vault Integration

### 4.1 Install Vault (dev mode + injector)

```bash
helm repo add hashicorp https://helm.releases.hashicorp.com
helm repo update
helm install vault hashicorp/vault \
  --set "server.dev.enabled=true" \
  --set "injector.enabled=true"
kubectl get pods
```

In this environment, direct HashiCorp repo access returned `403 Forbidden`, so Vault was installed via the official chart source repository:

```bash
git clone https://github.com/hashicorp/vault-helm.git /tmp/vault-helm
helm upgrade --install vault /tmp/vault-helm \
  --set "server.dev.enabled=true" \
  --set "injector.enabled=true" \
  --wait --timeout 300s
kubectl wait --for=condition=Ready pod/vault-0 --timeout=240s
```

### 4.3 Helm chart Vault support

Deployment supports Vault Agent injection via values:

- `vault.enabled`
- `vault.role`
- `vault.secretPath`
- `vault.injectFileName`
- `vault.injectTemplate`
- `vault.injectCommand`

When enabled, pod annotations are rendered:

```yaml
vault.hashicorp.com/agent-inject: "true"
vault.hashicorp.com/role: "devops-info-role"
vault.hashicorp.com/agent-inject-secret-config: "secret/data/myapp/config"
vault.hashicorp.com/agent-inject-template-config: |
  {{- with secret "secret/data/myapp/config" -}}
  APP_USERNAME={{ .Data.data.username }}
  APP_PASSWORD={{ .Data.data.password }}
  {{- end -}}
```

### 4.5 Sidecar injection pattern

- Vault injector mutates pod spec at admission time.
- A Vault Agent sidecar and shared volume are added automatically.
- Agent authenticates with Vault using pod service account JWT and writes secrets to files.
- App container reads local files, avoiding hardcoded credentials in image/manifests.

## 5. Security Analysis

### 5.1 Kubernetes Secrets vs Vault

- Kubernetes Secrets:
  - simple and built-in
  - good for basic workloads
  - requires cluster hardening (etcd encryption, RBAC, audit)
- Vault:
  - centralized secret lifecycle
  - stronger policy model and dynamic secret options
  - rotation and revocation workflows
  - better fit for production multi-service environments

### 5.2 When to use each

- Use Kubernetes Secrets for simple, low-risk, internal-only setups.
- Use Vault when you need rotation, fine-grained authz, auditability, and centralized management.

### 5.3 Production recommendations

- Never store real credentials in Git.
- Enable etcd encryption at rest in Kubernetes.
- Apply least-privilege RBAC for secrets.
- Prefer external manager (Vault) for sensitive or shared credentials.
- Rotate secrets regularly and verify applications reload changes safely.

## 6. Bonus - Vault Agent Templates and DRY env templates

### 6.1 Template annotation support

Implemented through `vault.injectTemplate` in `values.yaml` and rendered by deployment annotations.

This allows custom output format, for example `.env`:

```text
APP_USERNAME=...
APP_PASSWORD=...
```

### 6.2 Dynamic refresh and inject command

- Vault Agent can renew/re-render secrets based on lease/refresh behavior.
- `vault.hashicorp.com/agent-inject-command-<name>` can run a command after file update (for example, trigger app reload).
- This is exposed via `vault.injectCommand` in chart values.

### 6.3 Named template for env vars

Implemented named template:

- `define "devops-info.envVars"` in `k8s/devops-info/templates/_helpers.tpl`
- Included in deployment with:

```yaml
env:
  {{- include "devops-info.envVars" . | nindent 12 }}
```

Benefits:

- Removes duplicated env definitions.
- Keeps deployment template cleaner.
- Makes future env changes centralized and consistent.
